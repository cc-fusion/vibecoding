Four steps. One moving world.

MLS-MPM brings together the flexibility of particles and the simplicity of a grid. Each substep follows the same four stages as the original 88-line solver.

01

Start with a clean grid

Clear the grid’s mass and momentum. A compact 2D array stores the state, with a velocity and mass at every node.

02

Particles → grid (P2G)

Each particle shares its momentum with 9 nearby nodes using a quadratic B-spline. MLS-MPM forces and affine APIC momentum join the transfer.

03

Let the grid move

Normalize momentum by mass, add gravity, and enforce the boundaries. The grid only exists for this substep.

04

Grid → particles (G2P)

Gather the new velocity, rebuild the affine matrix C, move each particle, and update F. Snow also projects its deformation onto a plasticity limit.

vᵢ ← Σ wᵢₚ vₚ · Cₚ ← 4 Δx⁻¹ Σ wᵢₚ vᵢ dᵢₚᵀ

Three material models. Water uses a volume-pressure response. Jelly uses the fixed-corotated elastic model. Snow adds hardening and singular-value clamping. This is a 2D adaptation of the compact solver, not the full 3D CPIC/cutting package.

Where does it differ from the C++ source?

The P2G → grid update → G2P structure and APIC transfer are retained. JavaScript uses preallocated float32 arrays, separate vector components, an analytic 2×2 polar/SVD update, and a configurable particle budget. Particle volume is the unit grid cell’s area times 0.25. A frictional floor and constrained walls replace the original demo’s fixed boundary. It is not bitwise equivalent to the C++ version.

A few knobs, plenty of possibilities.

Pass an options object to the constructor. Changes to gravity and elasticity can be applied live with sim.setParameters().

OptionDefaultWhat it does
grid64Number of cells across the default square world. Higher values use more nodes and finer details.
aspect1World width ÷ height. A value of 2 creates 128 × 64 cells. Use your canvas aspect ratio.
dt0.0001Time in seconds per substep. Smaller values are more stable, but need more steps per frame.
material"water""water", "snow", or "jelly". Switch live with sim.setMaterial().
elasticity4000Young’s modulus, or the water bulk modulus. Lower values make the material softer.
gravity200Downward acceleration in world units per second squared. Zero gives weightlessness.
maxParticles16384Particle capacity, allocated once. Adding more than this limit throws a RangeError.
boundary3Wall thickness in grid cells. Lower values make the usable domain larger.
friction0.15Velocity retained at the floor each node update. Use 0 to 1.
seed12345Seed for repeatable jitter during particle creation. clear() resets the seed.

Start stable. Six substeps at dt = 0.0001 are a good starting point on a 64-cell grid. For faster devices, increase particle count rather than making the timestep arbitrarily large. High elasticity requires smaller timesteps.

Grid, aspect, and capacity are fixed at construction.

A small API. An open canvas.

The downloaded script exposes one global: MLSMPM. Use a Simulation to do the math and an optional Renderer to draw it. Both work without a framework.

new MLSMPM.Simulation(options)

Create an independent simulation. Useful public fields include count, time, steps, width, height, grid, and the typed arrays x, y, vx, vy, Fxx, Fxy, Fyx, Fyy, Cxx, Cxy, Cyx, and Cyy. See Configuration for all constructor options.

sim.addBox({ center, size, count, color, velocity })

Add a jittered rectangular particle block, with the center and size in world units. center defaults to [0.5, 0.5], size to [0.2, 0.2], count to 1000, color to a palette color, and velocity to [0, 0]. Returns the number of particles added. material is optional.

sim.addCircle({ center, radius, count, color, velocity })

Add a disk of particles. Uses the same arguments as addBox, except radius replaces size. Every shape receives the simulation’s current material, unless you specify one. Positions are in world units.

sim.addParticle(x, y, options) / sim.clear()

Add a single particle with optional velocity, material, and a CSS color. Returns its index. clear() removes all particles, resets the simulation clock, and re-seeds the random generator.

sim.step(count = 1)

Advance one or more fixed substeps. Returns the simulation. The simulation does not start a render loop by itself, so you control your own cadence. sim.step(6) is a convenient frame budget.

sim.setMaterial(name) / sim.setParameters(options)

Change the material of all existing particles, or update gravity, elasticity, dt, and friction. Switching material resets the deformation gradient and plastic volume to identity. Positions and velocities are preserved.

sim.applyImpulse(x, y, dx, dy, radius = 0.1, strength = 35)

Stir nearby particles with a smooth radial impulse. Coordinates and radius are in world units. dx and dy describe the pointer motion. The falloff keeps interactions local and smooth.

new MLSMPM.Renderer(canvas, sim, options)

Create a 2D Canvas renderer with an automatically sized, device-pixel-ratio-aware display. Options include background, pointSize, and grid. Call renderer.resize() when its container changes, and renderer.draw() to paint a frame. renderer.setGrid(false) toggles the guide grid.

Bring your own renderer. Access the public particle arrays and draw with Canvas, SVG, or WebGL. The renderer is optional; the solver has no DOM dependency.

Fast by design. Honest by default.

This is a CPU solver running in your browser’s main thread. It makes the most of small, predictable work instead of hiding behind an extra dependency.

  • Typed arrays, preallocated once

    All particle state and grid data live in compact arrays. The substep loop creates no new objects or short-lived weight arrays.

  • Small stencil, scalar math

    Each particle touches just nine grid nodes. Two-dimensional matrices are unrolled into scalar operations, including analytic snow plasticity.

  • Independent physics and rendering

    Choose your own substep budget and render cadence. The Canvas renderer batches particles by color instead of making a DOM element for every point.

Know the limits. A larger particle count, grid, or substep budget uses more CPU. The engine is not a worker, GPU, or WebAssembly solver. For demanding workloads, use a worker with a transferable state buffer or batch computation. This demo is for experimentation, not engineering validation.

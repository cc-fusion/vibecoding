Getting started

mls-mpm.js is a single file without dependencies. It defines one global, MLSMPM.

Installation

Quick start

This complete page reproduces main() of mls-mpm88.cpp: three blocks of snow falling into a box.

Three calls are all you need:

  • add_object(center, color) seeds 1000 particles in a 0.16 × 0.16 square, like the C++ function of the same name.
  • advance_frame() calls advance(dt) frame_dt / dt = 10 times, which is exactly what the C++ main loop does between two drawn frames.
  • render(canvas) draws the background, the box and the particles with the colors and radius of the C++ GUI.
Coordinates live in the unit square [0, 1]² with y pointing up, as in the C++ code. Use MLSMPM.pointer(event, canvas) to convert mouse and touch events.
02 · How it works

How MLS-MPM works

The Material Point Method keeps the material on particles (each carries position, velocity and deformation) and uses a background grid as a scratch pad on which forces and collisions are cheap to compute. MLS-MPM derives the particle ↔ grid transfers from a moving least squares approximation, so the elastic force rides along with the affine (APIC) momentum transfer. That is why the whole solver fits in 88 lines. Every call to advance(dt) runs three phases:

1

P2G · particles → grid

Each particle finds the 3 × 3 closest grid nodes and their quadratic B-spline weights w. It computes the fixed-corotated stress from its deformation gradient F (using the polar decomposition F = RS) and scatters mass, momentum and the fused stress + affine term:

mᵢ += w·m (mv)ᵢ += w·(m·v + A·(xᵢ − x))
A = −(4·Δt·vol / Δx²)·(2μ(F − R)Fᵀ + λ(J − 1)J·I) + m·C
2

Grid update

Momentum becomes velocity (divide by mass) and gravity is added. Then the box is enforced: nodes within boundary = 0.05 of the left, right or top wall are sticky (v = 0); at the floor only the downward component is removed (separate).

vᵢ = (mv)ᵢ / mᵢ + Δt·g
3

G2P · grid → particles

Each particle gathers its new velocity and affine matrix C, moves, and updates F. Snow then clamps the singular values of F and stores the discarded volume change in Jp, which hardens the material: μ, λ ∝ e^(ξ(1 − Jp)).

v = Σ w·vᵢ C = (4 / Δx²)·Σ w·vᵢ(xᵢ − x)ᵀ
x += Δt·v F ← (I + Δt·C)·F Σ ← clamp(Σ, 1 − θc, 1 + θs)

Particles and materials

A particle is exactly the C++ struct Particle plus a material id. Instead of an array of objects, every field lives in its own typed array (a structure of arrays):

C++ fieldJavaScriptPer particleMeaning
Vec xsim.x2 × Float64Position in [0, 1]²
Vec vsim.v2 × Float64Velocity
Mat Fsim.F4 × Float64Deformation gradient (elastic part), row-major, starts as the identity
Mat Csim.C4 × Float64Affine velocity field (APIC), row-major
real Jpsim.Jp1 × Float64Plastic volume ratio; drives hardening
int csim.c1 × Uint32Color 0xRRGGBB
(none)sim.material1 × Uint8SNOW, JELLY or WATER (extension)
MaterialBehaviourOrigin
MLSMPM.SNOW · 0 · defaultFixed-corotated elasticity + snow plasticity and hardening (Stomakhin et al. 2013). Crumbles, compacts and stays deformed.C++ with plastic = true
MLSMPM.JELLY · 1The same elasticity, but never plastic: always springs back to its rest shape.C++ with plastic = false
MLSMPM.WATER · 2μ = 0 and F is reset to √J·I every step: a weakly compressible fluid.Extension, as in Taichi's mpm99.py

Materials can be mixed freely in one simulation: pass { material: 'water' } (or MLSMPM.WATER) to add_object or add_particle.

C++ → JavaScript mapping

Every global, type and function of mls-mpm88.cpp has a direct counterpart. The names are kept identical (snake_case), so the two files can be read side by side.

mls-mpm88.cppmls-mpm.js

Side by side

The JavaScript advance() follows the C++ function line by line, including its comments. The differences are mechanical: the particle struct becomes typed arrays, 2 × 2 matrix algebra is unrolled into scalars, and the loops never allocate. Two small additions are marked in the code: optional hooks (attractor, grid_hook) in the grid update, and a position clamp that keeps particles inside the grid, a safety net that never triggers in normal scenes. The grid also keeps each node's mass after normalization, so you can visualize it.

03 · API reference

API reference

new MLSMPM(options?)

Creates a simulation. Every option is optional and the defaults are the constants of mls-mpm88.cpp. All options also become live properties, so you can change sim.E, sim.gravity or sim.plastic at any time (only n is fixed).

OptionDefaultC++Description

dt1e-4 × 80 / ndtSubstep size: 1e-4 at n = 80, smaller on finer grids so the explicit integrator stays stable.
frame_dt1e-3frame_dtSimulated time per advance_frame().
particle_mass1particle_massMass of every particle.
vol1volVolume of every particle.
E1e4EYoung's modulus: stiffness.
nu0.2nuPoisson's ratio, between 0 and 0.5: how strongly the volume is preserved.
hardening10hardeningSnow hardening ξ: μ and λ are scaled by e^(ξ(1 − Jp)).
plastictrueplasticSnow plasticity on or off (affects SNOW particles only).

theta_s0.00757.5e-3_fCritical stretch: singular values of F are clamped to at most 1 + θs.
gravity[0, −200]Vector3(0, -200, 0)Gravitational acceleration (x, y).
boundary0.05boundaryWall thickness. Left, right and top walls are sticky; the floor separates.
seedMath.random(none)Integer seed for the PRNG used by add_object, for reproducible scenes.

Methods

sim.add_object(center, c, options?) → number

Seeds particles uniformly at random in a square; this is the C++ add_object. Returns the index of the first new particle: the object occupies indices first … first + count − 1.

center[x, y]: center of the square.
cColor, 0xRRGGBB.
options.sizeHalf-size: a number (default 0.08, a 0.16 × 0.16 square) or [half_width, half_height].
options.countNumber of particles. The default keeps the C++ density: 1000 for the default square at n = 80, scaled with area and n².
options.velocityInitial velocity [vx, vy]; default [0, 0].
options.material'snow' (default), 'jelly', 'water', or MLSMPM.SNOW / JELLY / WATER.
sim.add_particle(x, c, options?) → number

Adds a single particle at x = [x, y] with color c; this is C++ particles.push_back(Particle(x, c, v)). options.velocity and options.material work as above. Returns the particle index. Use it to build any shape.

sim.advance(dt?) → sim

Runs one substep (P2G, grid update, G2P); this is the C++ advance(dt). dt defaults to sim.dt.

sim.advance_frame() → sim

Runs sim.steps_per_frame = round(frame_dt / dt) substeps, 10 by default: one visual frame of the C++ main loop.

sim.render(target, options?) → sim

Draws the scene into a canvas element, an OffscreenCanvas or a 2D context, the way the C++ GUI does. Particles are written straight into an ImageData pixel buffer, so it stays fast with tens of thousands of particles.

options.backgroundBackground color, default 0x112F41. null leaves the canvas transparent.
options.boxColor of the 0.04 to 0.96 box, default 0x4FB99F. null hides it.
options.radiusParticle radius in pixels. Default: 2 px per 800 px of canvas, like the C++ GUI.
sim.clear() → sim

Removes all particles and resets sim.t to 0.

sim.reserve(capacity) → sim

Pre-allocates the particle arrays, so they are never re-allocated while adding particles.

sim.get_particle(i) → { x, v, F, C, Jp, c, material }

Returns a copy of a particle's state as plain arrays and numbers, which is handy for debugging. For bulk access, read the typed arrays directly.

06 · Performance

Performance

advance() is written the way you would write a C kernel:

  • Structure of arrays. Particle fields live in flat Float64Arrays instead of one object per particle. They are compact, cache-friendly and monomorphic for the JIT.
  • Zero allocations per step. Weights, matrices and SVD results go to pre-allocated scratch buffers, so a running simulation never triggers garbage collection.
  • Closed-form 2 × 2 math. The polar decomposition and SVD use the same closed-form formulas as taichi.h, and matrix products are unrolled into scalar locals.
  • Pay only for what you use. The SVD is skipped for jelly and water (and for snow when plastic is off); the attractor and grid_hook branches cost nothing when unset.
  • Pixel-buffer rendering. render() writes particles straight into an ImageData buffer: one putImageData per frame instead of thousands of arc() calls.

Tips

  • Cost ≈ particles × substeps. The default add_object density (about 6 particles per cell) is a good balance; denser rarely looks better.
  • Stability. This is an explicit integrator: dt must shrink as the material gets stiffer or the grid finer (roughly dt ∝ Δx / √E). That is why dt defaults to 1e-4 × 80 / n. If a scene explodes, lower E, nu or dt.
  • Heavy scenes. Run the simulation in a Web Worker and post sim.x to the main thread for drawing.
  • Pause off-screen simulations. This page does that with an IntersectionObserver.
